# 审查工作流

## 审查前

1. 读取项目说明、仓库规则、入口、构建和依赖文件、测试、配置、部署清单与文档。
2. 建立项目画像，区分代码事实、执行结果、文档声明和待确认信息。
3. 根据项目类型和风险选择规则，并记录不适用原因。

## 审查中

按“需求边界 → 架构模块 → 代码配置 → 接口数据 → 测试门禁 → 安全性能 → 观测交付 → 恢复演进”检查。每条发现都绑定路径和尽可能精确的行号；能够执行时用命令或测试复现，不以静态猜测替代运行证据。

文件和目录结构审查重点：

- 是否存在上帝类、过大组件、超长方法、职责混杂、循环依赖和高冲突文件。
- 是否单个目录文件过多、同类文件分散、命名不稳定或存在重复模板。
- 拆分建议是否能降低变化耦合、测试难度或协作冲突，而不是仅增加文件数量。

## 输出

使用 [审查报告模板](../templates/review-report-template.md)。问题至少包含状态、级别、位置、证据、风险、整改建议、验收标准和发布门禁。结论只能基于证据，并明确剩余风险、待确认和未验证项。
