# 实施工作流

## 开始前

- 读取仓库级指令、目录级约定、当前分支和工作区差异。
- 用项目画像确认项目类型、运行方式、风险、外部依赖和本次变更边界。
- 选择必要规则，不因为“通用工程化”而加载或实施无关技术。
- 写出最小实施计划，明确不改动的范围、验收标准和失败时的回退方式。

## 设计与拆分

1. 先定位领域边界、入口和数据流，再决定文件位置。
2. 让控制器/页面负责编排，让业务层承载规则，让数据访问层负责持久化，让适配层隔离外部系统。
3. 超长方法按步骤、变化原因或可测试边界拆分；过大文件按职责拆分；重复流程优先抽取稳定的共享能力。
4. 新增目录前确认现有目录是否已有同类职责；目录直接子文件接近 8–12 个时评估按领域或资源类型分组。
5. 避免为了拆分制造只有一行转发的文件、循环依赖、过度泛化的工具类和无法定位业务语义的“万能”模块。

## 编码中的完成定义

每个核心行为变更至少检查：

- 成功、失败、空值、边界、重复、超时、并发和权限分支中与风险相关的部分。
- 配置默认值、错误处理、日志上下文、指标、审计、兼容和资源释放。
- 需要数据或接口变化时，迁移、版本、幂等、回滚和客户端兼容。
- 需要用户可见变化时，加载、空态、错误态、无权限、可访问性和浏览器/设备兼容。
- 公共接口、复杂规则和非直观副作用的文档；遵循仓库注释规范。

## 实施后

- 先运行快速反馈检查，再运行与风险匹配的完整门禁。
- 检查新增文件是否有测试、文档或明确的不适用理由。
- 对差异做一次结构审查：是否越界、是否重复、是否引入过大文件或目录、是否留下调试代码和秘密。
- 输出变更总结、测试证据、未验证项、发布影响和回滚方式。
