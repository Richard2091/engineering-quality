# Skill 自身的维护规范

本文件约束的是 `engineering-quality` 这个 Skill 的可维护性，不是要求业务仓库照搬该目录。

## 结构

- `SKILL.md` 只保留定位、模式路由、核心流程、权限边界、规则索引和输出顺序。
- `references/baseline/` 放跨项目共用的稳定基线。
- `references/project-types/` 放按技术形态启用的专项规则；一个文件聚焦一个项目类型或紧密主题。
- `references/workflows/` 放实施、审查、整改等生命周期流程。
- `references/templates/` 放可直接复制填写的画像、计划、报告、门禁和总结模板。
- `roadmap.md` 只记录后续增强方向和优先级，不把未实现能力写成现行规则。

## 规模与拆分

- `SKILL.md` 建议控制在约 250–350 行以内；超过后优先把条件性内容移入参考文件。
- 单个参考文件建议控制在约 250–400 行以内；超过后按主题、项目类型或生命周期拆分。
- 单个目录建议不超过约 8–12 个直接子文件；超过时按领域分组。
- 上述数字是维护信号，不是机械质量门禁。拆分必须降低职责耦合、阅读成本、测试难度或协作冲突。
- 不创建空目录、重复规则、只有转发内容的文件或没有使用路径的“装饰性”模板。

## 内容质量

- 所有引用路径必须存在；移动文件后同步更新索引和交叉引用。
- 规则写“何时启用、检查什么、需要什么证据、如何验收”，不要把抽象口号写成强制技术选型。
- 区分现行规则、建议规则、待确认项和未来规划；每条强制要求都应有风险依据。
- 模板必须包含上下文、责任、证据、验收和剩余风险等字段，能够直接用于真实任务。
- Markdown 文件统一使用 UTF-8；中文标点和术语保持一致，避免同一概念多种叫法。

## 变更与验证

每次修改 Skill 后至少执行：

1. 使用 UTF-8 环境执行 `python -X utf8 "C:\\Users\\Windows\\.codex\\skills\\.system\\skill-creator\\scripts\\quick_validate.py" "D:\\Program\\AIProject\\engineering-quality"`，校验元数据和未完成占位符。
2. 执行本 Skill 的 `scripts/validate_structure.py`，检查所有 Markdown 引用路径、重复文件、模板字段和目录规模。
3. 检查规则索引中的文件均存在，模板均非空且包含实际字段；脚本失败时不得宣称验证通过。
4. 使用一个真实的实施请求和一个已有项目审查请求做独立前向测试。
5. 记录本次变更解决的问题、未覆盖领域和下一步路线图。
